# PoC-04: 送り切りと収集器

- 優先: P0（M0 の対象）
- 決まること: [ADR-006](../decisions.md#adr-006-送り切りは同期送信で担保する)、[ADR-007](../decisions.md#adr-007-収集器の選択)
- 関連: [MicroVMs の設計 7 章](../design/microvms.md#7-送り切りadr-006)

## 目的

停止と終了の直前に出たテレメトリが、取りこぼしなく届くかを確かめます。あわせて、Alloy と Rotel を比べます。

## 前提

- [共通の安全策](README.md#共通の安全策) を満たしています。
- LGTM 側は Grafana Cloud の無料枠、CloudWatch 側は同じアカウントの OTLP エンドポイントを使います。
- 検証用の小さな中継スクリプト（本番の kagero の代わり）で、フックの順序を再現します。

## 手順

1. `/suspend` と `/terminate` の直前に、連番つきのログ・span・メトリクスを一気に出すアプリを用意します。
2. 3 つの送り方を比べます。
   - (a) 通常の設定（バッチ処理あり）
   - (b) 同期送信の設定（バッチ処理なし、送信キューなし）
   - (c) (b) に加えて、終了時に収集器へ SIGTERM を送り、終了を待つ
3. 各方式を、LGTM と CloudWatch で 20 回ずつ試し、届いた連番を数えます。
4. 送り先に届かない状態（誤ったエンドポイント）にして、フックが時間の上限の中で返るか、アプリが止まらないかを確かめます。
5. Alloy と Rotel で、次の値を測ります。
   - 常駐メモリ
   - 起動にかかる時間
   - 設定の再読込にかかる時間
   - スナップショットの大きさの増え方
   - CloudWatch へ SigV4 で送れるか
6. 同期送信によるアプリの遅れ（flush にかかる時間）を測ります。

## 合格条件

- (b) か (c) で、両方のバックエンドとも 99.9% 以上の連番が届くこと。
- 送り先が落ちていても、フックが時間の上限の中で返り、アプリが止まらないこと。
- Alloy と Rotel の比較表が埋まること。

## 費用と後片付け

- 費用の目安: 2 GB の MicroVM を延べ 40 回、各 10 分動かして約 $0.84 です。CloudWatch への取り込みは少量です。合計で $2 未満を見込みます。
- この PoC の MicroVMs には、PoC-09 で費用を照合するためのタグを付けておきます。
- 後片付け: [チェックリスト](README.md#後片付けチェックリスト) をすべて確かめます。
