# PoC-05: バックエンドの違い

- 優先: P0（M0 の対象）
- 決まること: [ADR-002](../decisions.md#adr-002-最初から-2-つのバックエンドに対応する)（違いの一覧）、[ADR-008](../decisions.md#adr-008-識別とカーディナリティ)、[ADR-010](../decisions.md#adr-010-ダッシュボードとアラートの仕様)
- 関連: [全体設計 5 章](../design/architecture.md#5-2-つのバックエンド)

## 目的

同じ OTLP のデータが、LGTM と CloudWatch でどう見えるかを確かめます。1 つの仕様から 2 つのダッシュボードを作れるかの判断材料にします。

## 前提

- [共通の安全策](README.md#共通の安全策) を満たしています。
- LGTM 側は Grafana Cloud の無料枠を使います。
- CloudWatch 側は、Grafana から Amazon Managed Prometheus のデータソース（`sigv4Service=monitoring`）で問い合わせます。

## 手順

1. 決まった内容の OTLP データを用意します。次を含めます。
   - カウンター、ゲージ、ヒストグラム
   - delta と cumulative の両方
   - 単位つきの名前、UTF-8 の名前
   - リソース属性
2. 同じデータを、LGTM と CloudWatch の両方に送ります。
3. 両方で PromQL を実行し、メトリクス名・ラベル・値の対応表を作ります。
4. CloudWatch PromQL の 500 系列の上限が、入力と出力のどちらの系列数に効くかを確かめます。
5. **複数 writer の累積カウンタを確かめます（重要）。** ADR-008 で個体 ID をラベルから外した結果、同じイメージの全 MicroVM が完全に同一のラベル集合を持ちます。cumulative temporality では N 台のエージェントが 1 つの系列に独立した累積値を書き込み、`rate()` / `increase()` が偽のリセットを拾って真値を超過します（OTLP の single-writer 原則）。delta temporality にするか、書き込み側で単一 writer に寄せるかを、この PoC で確かめて ADR に反映します。単一 VM では発覚しません。
6. `AWS/Lambda` の標準メトリクスを、リソースタグを付けて PromQL で問い合わせます。名前とラベルを記録します。
7. 同じパネルの定義を、両方のデータソースで表示できるかを確かめます。
8. ダッシュボードを 1 回更新したときに課金されるサンプル数を記録し、GetMetricData の場合と比べます。

## 合格条件

- 名前・ラベル・値の対応表ができること。
- 共通の定義のパネルが、1 つ以上両方で動くこと。
- 費用の比較（PromQL と GetMetricData）を、数値で記録できること。

## 費用と後片付け

- 費用の目安: 取り込みと問い合わせは少量で、合計 $1 未満を見込みます。
- 後片付け: [チェックリスト](README.md#後片付けチェックリスト) をすべて確かめます。
