# PoC-02: フックの振る舞い

- 優先: P0（M0 の対象）
- 決まること: [ADR-004](../decisions.md#adr-004-フックの順序つき中継)（失敗時の扱いと時間の配分）
- 関連: [MicroVMs の設計 5 章](../design/microvms.md#5-フックの中継adr-004)

## 目的

ライフサイクルフックの実際の振る舞いを、表にまとめます。kagero の中継の設計は、この表を土台にします。

## 前提

- [共通の安全策](README.md#共通の安全策) を満たしています。
- 実行時のフックの時間上限は、試しやすい値（例: 10 秒）に設定します。

## 手順

1. テスト用のアプリを作ります。フックごとに、返事までの遅れと、返すステータスを切り替えられるようにします。
   - 遅れ: 0 秒、上限の半分、上限を超える時間
   - ステータス: 200、404、500、503
2. すべての組み合わせで、MicroVM の状態の変化と、Lambda の再試行の有無を記録します。
3. 停止を 2 通りで起こします。idle policy による自動停止と、`suspend-microvm` の API です。どちらでも `/suspend` が呼ばれるかを確かめます。
4. `maximumDurationInSeconds` に達したときに、`/terminate` が呼ばれるかを確かめます。
5. フックのポートに、外から届くかを確かめます。認証トークンの許可ポートに含めた場合と、含めない場合を試します。
6. 自動停止と自動再開が、CloudTrail に残るかを確かめます。
7. 同じフックが 2 回呼ばれることがあるかを記録します。
8. フックの送信元のアドレスを記録します。`KAGERO_HOOK_ALLOWED_PEERS` に設定する値になります。未設定のままでは、アプリが MicroVM 自身の IP からフックを偽造できます（[脅威モデル](../design/architecture.md#9-脅威モデル)）。

## 合格条件

- フックごとに、状態の変化・時間上限を超えたときの動き・再試行の有無の表が埋まれば合格です。
- 許可ポートに含めなければ、フックのポートに外から届かないこと。届く場合は、ADR-004 と脅威モデルを見直します。

## 費用と後片付け

- 費用の目安: 0.5 GB の MicroVM を延べ 10 回、各 10 分動かして約 $0.05 です。合計で $1 未満を見込みます。
- 後片付け: [チェックリスト](README.md#後片付けチェックリスト) をすべて確かめます。
