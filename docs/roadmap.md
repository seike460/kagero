## 原則

- 早く出します。MicroVMs は、AWS が公式のメトリクスを出す前に v0.1 を出すことを目標にします。
- PoC で確かめてから作ります。M0 の PoC ゲートを通るまで、実装コードは書きません（実装が先行した件の記録は [ADR-012](decisions.md)）。
- 段階ごとに「入れないもの」を決めます。1 人で保守できる量に保つためです。
- 共通部品は、先に作り込みません。A と B で実際に必要になった形に育てます。
- C と D は、v1.0 まで実験扱いにします。

| v0.1 MicroVMs プレビュー | re:Invent 2026 の前（例年 11 月末〜12 月初め） | 下の「v0.1 の合格条件」を満たします | eBPF、コスト、fleet 表示、CDK constructs、アラート |

### v0.1 の合格条件

1. 停止・終了の直前に送ったテレメトリの 99.9% 以上が、両方のバックエンドに届きます（各 20 回の試行）。
2. すべての span とログに、MicroVM の ID が付きます。
3. 同じイメージから起動した 10 台で、trace ID が重なりません。
4. フックの処理にかかる時間が、PoC で決めた予算の中に収まります。
5. 送り先が落ちていても、アプリの処理は止まりません。
6. simulator での E2E テストが、CI で通ります。
7. 生成したダッシュボードが、Grafana 13 と Amazon Managed Grafana 12.4 で読み込めます。

## 状況が変わったときの分岐

- PoC で A（MicroVMs）が詰まった場合は、B（Lambda 関数）を先に進めます。A は、詰まった点が解けてから再開します。
- AWS が MicroVMs の公式メトリクスを出した場合は、それを読む adapter を足します。そのうえで、中での正しさ（識別と送り切り）とコストに重心を移します。
- Durable Functions の公式の OTel プラグインが直った場合は、D の役割を「再実行と費用の分析」に寄せます。
- Grafana が同じ機能を出した場合は、自前の LGTM と Amazon Managed Grafana の利用者に重心を移します。

## 版の付け方

- SemVer を使います。0.x の間は、互換性を保証しません。
- モノレポ全体で、1 つの版にします。
- 段階を終えるたびに、minor を上げます（v0.1.0、v0.2.0 など）。

## 対象外

- Grafana 本体を Lambda で動かすこと
- Lambda を呼び出すデータソースのプラグイン
- AI による障害対応（AI SRE）
- 独自の Lambda extension（v1.0 まで）
- UI と、ブラウザを使う負荷試験

## 上流への貢献（v1.0 までに）

- OpenTelemetry の `telemetryapi` receiver に、費用の指標を足す PR を出します。
- MicroVMs 向けの属性を、OpenTelemetry のセマンティック規約に提案します。
- Grafana Foundation SDK に、サーバーレスの例を提供します。
- grafana.com に、ダッシュボードを公開します。
