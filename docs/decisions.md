# 設計判断の記録（ADR）

- 最終更新: 2026-09-26
- 状態の意味: 「採用」は決定済みです。「提案」は PoC の結果で決めます。「却下」は採らなかった案です。
- 新しい ADR は、末尾に番号を足して書きます。決定を変えるときは、古い ADR を消さずに「置き換え」と書きます。

## 書式

```markdown
## ADR-NNN: 題名

- 状態: 提案 / 採用 / 却下 / ADR-MMM で置き換え
- 日付: YYYY-MM-DD
- 確かめる PoC: PoC-NN（なければ「なし」）

### 背景
### 決定
### 理由
### 影響
```

## ADR-001: モノレポと言語の分担

- 状態: 採用
- 日付: 2026-09-26
- 確かめる PoC: なし

### 背景

kagero は、4 つのモジュールと共通部品を持ちます。MicroVM の中で動く部品と、AWS の外側で動く部品では、求められる性質が違います。

### 決定

- 1 つのリポジトリ（モノレポ）にまとめます。
- MicroVM の中で動くエージェントだけを Rust で書きます。
- 制御用の Lambda、CDK constructs、ダッシュボードの生成、simulator は TypeScript（Node.js 24）で書きます。

### 理由

- エージェントは、利用者のあらゆるイメージに入り込みます。メモリとスナップショットを小さく保つ必要があります。単一のバイナリで入れられ、プロセスと権限を直接操作できる Rust が合います。
- CDK と Grafana Foundation SDK には、Rust 版がありません。
- 制御用の Lambda は呼ばれる回数が少なく、コールドスタートの差が効きません。CDK と同じ道具で完結する TypeScript の方が、速く作れます。

### 影響

- Rust で書く範囲は、エージェント 1 つに限られます。
- CI は、Rust と TypeScript の 2 系統を持ちます。

## ADR-002: 最初から 2 つのバックエンドに対応する

- 状態: 採用
- 日付: 2026-09-26
- 確かめる PoC: PoC-05（違いの洗い出し）

### 背景

Grafana の利用者には、LGTM（Grafana Cloud や自前の Loki・Tempo・Mimir）を使う人と、CloudWatch を使う人がいます。CloudWatch は 2026-06 に OTLP の受信と PromQL に対応しました。

### 決定

- LGTM と CloudWatch の両方に、最初から対応します。
- 両方へ同時に送る設定も用意します。

### 理由

- AWS だけで完結させたい利用者と、Grafana の本流に乗りたい利用者の両方に届けるためです。
- CloudWatch の PromQL 対応で、同じ PromQL の仕様を両方に使える見込みが立ったためです。

### 影響

- すべての機能で、両方のバックエンドでの動きを決める必要があります。出せない場合は「非対応」と明示します。
- 最初の公開までの作業量が増えます。

## ADR-003: Apache-2.0 と非公式の表示

- 状態: 採用
- 日付: 2026-09-26
- 確かめる PoC: なし

### 決定

- ライセンスは Apache-2.0 にします。
- README に、AWS と Grafana Labs の公式のものではないと明記します。
- 名前に AWS・Grafana・Lambda の商標を入れません。
- k6（AGPL-3.0）を同梱する場合は、改変せずに、ライセンスの条件に従って表示します。

### 理由

- OpenTelemetry や Grafana Alloy と同じライセンスで、組み合わせやすいためです。
- 特許の許諾を含み、企業でも使いやすいためです。

## ADR-004: フックの順序つき中継

- 状態: 提案
- 日付: 2026-09-26
- 確かめる PoC: PoC-02

### 背景

MicroVMs のフックを受けるポートは 1 つだけです。アプリと計測の両方が、フックを必要とします。

### 決定（案）

- `kagero` をコンテナの起動役（PID 1）にし、フックの受け口にします。
- フックを、決まった順でアプリに中継します。`/run` と `/resume` は kagero が先、`/suspend` と `/terminate` はアプリが先です。
- 実行時の失敗では業務を止めません。ビルド時の失敗ではビルドを止めます。

### 却下した案

- 複数のプロセスへの一斉配信: 順序と時間の配分を保証できないためです。

### 影響

- 利用者は、ENTRYPOINT を kagero に変える必要があります。

## ADR-005: ビルド時は静止し、/run で起動する

- 状態: 提案
- 日付: 2026-09-26
- 確かめる PoC: PoC-03

### 背景

スナップショットには、乱数の状態や開いた接続も写ります。同じイメージから起動した MicroVM は、すべて同じ状態から始まります。

### 決定（案）

- ビルド時には、ID・乱数の種・接続・秘密情報を作らず、テレメトリも送りません。
- `/run` で個体情報を作り、収集器を設定し、アプリが OTel SDK を初期化します。
- 収集器をビルド時に起動しておくか、`/run` で初めて起動するかは、PoC-03 と PoC-04 の結果で決めます。

### 影響

- アプリには、OTel SDK の初期化を `/run` に置いてもらう必要があります。例を用意します。

## ADR-006: 送り切りは同期送信で担保する

- 状態: 提案
- 日付: 2026-09-26
- 確かめる PoC: PoC-04

### 決定（案）

- 収集器を同期送信の設定にします。バッチ処理と送信キューを使いません。
- `/suspend` と `/terminate` では、アプリの flush、kagero の送信の順に進めます。`/terminate` では最後に収集器を止めます。

### 却下した案

- 収集器のキューの数値を見て待つ案: バッチの中や送信中のデータが見えないためです。
- kagero 自身を OTLP の中継点にする案: 収集器を作り直すことになり、保守の負担が大きいためです。

### 影響

- 送信のたびに受け取りを待つため、アプリの遅れが増えます。量は PoC-04 で測ります。

## ADR-007: 収集器の選択

- 状態: 提案
- 日付: 2026-09-26
- 確かめる PoC: PoC-04

### 決定（案）

- Grafana Alloy を既定にします。
- Rust 製の Rotel を比べる対象にします。
- 判断の基準は、同期送信での送り切りの確実さ、常駐メモリ、起動と再読込の時間、CloudWatch への SigV4 送信の対応です。

### 理由

- Alloy は Grafana の公式の収集器で、LGTM との相性が良いです。
- MicroVMs では、常駐メモリがスナップショットの大きさを通じて費用に響きます。軽い Rotel が有利になる可能性があります。

## ADR-008: 識別とカーディナリティ

- 状態: 提案
- 日付: 2026-09-26
- 確かめる PoC: PoC-05

### 決定（案）

- `service.instance.id` に MicroVM の ID を入れます。
- MicroVM・テナント・セッション・リクエストの ID は、ログと trace にだけ付けます。メトリクスのラベルには入れません。
- テナントとセッションの ID は、アプリが明示した場合だけ付けます。
- 識別属性は、収集器の側で上書きします。
- 規約にない属性には `kagero.` を頭に付け、定義は Weaver の YAML にまとめます。

### 理由

- CloudWatch PromQL は、1 クエリ 500 系列が上限です。Mimir でも、系列の入れ替わりが負担になります。

## ADR-009: コストモデル

- 状態: 提案
- 日付: 2026-09-26
- 確かめる PoC: PoC-09

### 決定（案）

- エージェントは使用量の事実だけを送ります。単価はクエリ側で掛けます。
- 単価表は、リージョン・アーキテクチャ・適用開始日で引ける、版つきのファイルにします。
- 表示はすべて「推定」とし、請求データ（CUR）との照合結果を公開します。

### 理由

- エージェントは、停止中と終了後に動けません。
- 単価をエージェントに埋め込むと、改定のたびにイメージの作り直しが必要になります。

## ADR-010: ダッシュボードとアラートの仕様

- 状態: 提案
- 日付: 2026-09-26
- 確かめる PoC: PoC-05、PoC-06

### 決定（案）

- Grafana Foundation SDK（TypeScript）で、1 つの仕様を書きます。
- バックエンドごとの adapter で、LGTM 用と CloudWatch 用に分けて出力します。
- 出力は v1 の JSON にします。生成物は commit し、CI で再生成の差分を確かめます。
- 片方で出せないパネルは、「非対応」と書いたテキストパネルにします。

### 理由

- 2 つのバックエンドを、別々の手書きの JSON で保守すると、作業が 2 倍になるためです。
- Amazon Managed Grafana 12.4 は schema v2 に対応していないためです。

## ADR-011: 秘密情報の渡し方

- 状態: 提案
- 日付: 2026-09-26
- 確かめる PoC: PoC-01

### 決定（案）

- 秘密情報を、イメージの環境変数と `runHookPayload` に入れません。
- `/run` の時点で、実行ロールを使って Secrets Manager から取ります。
- 送信用の認証情報は、書き込み専用・範囲限定・短命のものにします。
- CloudWatch へ送る場合は、実行ロールの SigV4 を使い、秘密情報を持ちません。

### 理由

- イメージの環境変数は、すべての MicroVM で共有され、スナップショットにも写るためです。
- MicroVM の中のアプリは、信頼できないコードかもしれないためです。

### 影響

- アプリから実行ロールの資格情報に届いてしまうかは、PoC-01 で確かめます。届く場合は、実行ロールの権限を最小にします。

## ADR-012: M0 ゲート前の実装（逸脱の記録）

- 状態: 採用
- 日付: 2026-09-26
- 確かめる PoC: すべての PoC

### 背景

- ロードマップと AGENTS.md は、「M0 の PoC ゲートを通るまで実装コードを書かない」と定めていました。
- 2026-09-26 時点で、AWS の認証情報が開発環境に設定されておらず、実機の PoC を実行できません。
- 作業の依頼により、実機 PoC を待たずに v0.1〜v0.4 相当の実装を先に進めました。

### 決定

- 実装を先行させます。検証は、AWS の実機の代わりに、次の方法で行います。
  - packages/sim が実際のエージェントのバイナリを HTTP で駆動する E2E テスト
  - ユニットテスト、型検査、lint、生成物の差分検査を含む CI の全ゲート
  - 生成したダッシュボード・アラート・CDK テンプレートの検査
- 「提案」の ADR は、対応する PoC が実機で確かめるまで、状態を「採用」に変えません。
- 実装中に見つかった仕様の不確かさ（イベントの形・API の値域・製品の制限）は、公開ドキュメントで裏付けてから実装しました。裏付けられなかった点は、PoC の手順書に「確かめること」として追記しています。
- 実装と設計がずれた点は、各 PoC で最初に確かめる候補とします。

### 理由

- 実機が使えなくても、契約（フックの順序・送り切り・識別・カーディナリティ）はシミュレーションで確かめられるためです。
- 実装を先に出すことで、PoC 実施時に「動くものを確かめる」形に進められるためです。

### 影響

- 実機でしか分からない性質（タイムアウトの実値・資格情報の到達範囲・料金の実額・スナップショットの実挙動）は、すべて未検証のままです。README の実装状況表に、検証方法を併記します。
- PoC が設計と違う実態を示した場合、実装側を直します。設計を変える場合は、新しい ADR を足します。
